# بررسی فنی و اصلاحات (Technical Review)

این سند خلاصه‌ی بررسی فنی کامل پروژه، ایرادهای پیداشده و اصلاحات انجام‌شده است.
همه‌ی موارد پس از اصلاح با `npm run lint` + `npm run typecheck` + `npm test` + `npm run build` و
آزمون دود سرتاسری `npm run smoke` (دانلود واقعی MP4 و MP3) بررسی شده‌اند.

---

## ۱) ایرادهای بحرانی و رفتاری (اصلاح‌شده)

| # | مشکل | تأثیر | اصلاح |
|---|---|---|---|
| ۱ | **پرش عقب نوار پیشرفت در دانلودهای ادغامی** — yt-dlp برای `-f 137+140` می‌نویسد «Downloading **1** format(s)» ولی دو استریم جدا دانلود می‌کند؛ شمارش مرحله‌ها از همان عدد خوانده می‌شد | پیشرفت از ~۹۵٪ به ۰٪ برمی‌گشت و کاربر فکر می‌کرد دانلود از نو شروع شده | شمارش از خودِ فهرست فرمت‌ها (`137+140` → ۲) در ماژول جدید `src/lib/progress.ts` + آزمون واحد مخصوص همین سناریو |
| ۲ | **امکان تحویل فایل نیمه‌کاره** — انتخاب خروجی با «اولین فایل با پسوند mp4» انجام می‌شد | می‌توانست `output.f137.mp4` (فایل موقت ادغام) را به‌جای `output.mp4` بفرستد | `pickOutputFile()` با اولویت نام دقیق `output.<ext>` و کنار گذاشتن فایل‌های موقت/جانبی |
| ۳ | **بازسازی هر ثانیه‌ای polling در کلاینت** — افکت به `activeJobs` وابسته بود | اینتروال هر ثانیه ساخته/نابود می‌شد، برخی وضعیت‌ها گم می‌شد و API بی‌دلیل فشار می‌دید | کلید پایدار `activeKey` (فهرست jobهای فعال) به‌عنوان وابستگی افکت |
| ۴ | **گیر کردن jobها پس از ری‌استارت سرور** | رکوردها تا ابد در وضعیت «در حال دانلود» می‌ماندند | بازبینی زمان راه‌اندازی: jobهای نیمه‌کاره به «خطا» تغییر می‌کنند و پوشه‌شان پاک می‌شود |
| ۵ | **نبود محدودیت دانلود هم‌زمان** | چند دانلود موازی می‌توانست CPU/رم/دیسک سرور را اشباع کند | صف واقعی با `MAX_CONCURRENT_DOWNLOADS` و وضعیت `pending` + شماره‌ی نوبت (وضعیت `pending` در schema بود اما هرگز استفاده نمی‌شد) |
| ۶ | **ساخت دانلود تکراری** — کلیک دوباره روی همان کیفیت | jobهای تکراری و مصرف بی‌دلیل منابع | تشخیص تکراری (url + نوع + کیفیت) و پاسخ ۲۰۰ با `reused: true` |
| ۷ | **کشتن ناقص فرایند هنگام لغو** — فقط yt-dlp کشته می‌شد | ffmpeg فرزند می‌توانست به کار خود ادامه دهد و فایل نیمه‌کاره بسازد | اجرای فرایند در گروه جدا (`detached`) و کشتن کل گروه (SIGTERM → SIGKILL پس از ۳ ثانیه) |
| ۸ | **نبود `pool.on("error")` در pg** | خطای یک کلاینت بی‌کار (ری‌استارت دیتابیس) به‌صورت unhandled error کل سرور را crash می‌کرد | هندلر خطا + ساخت pool فقط در صورت وجود `DATABASE_URL` + `statement_timeout` |
| ۹ | **نبود timeout در استخراج اطلاعات ویدئو** | یک yt-dlp هنگ‌کرده، درخواست `/api/info` را بی‌نهایت باز نگه می‌داشت | `runCapture` با timeout و کشتن فرایند (`YTDLP_INFO_TIMEOUT_MS`) |
| ۱۰ | **`--no-check-certificates`** | اعتبارسنجی گواهی TLS برای همه‌ی درخواست‌های yt-dlp غیرفعال بود (خطر MITM) | حذف شد (در صورت نیاز خاص با `YTDLP_EXTRA_ARGS` قابل بازگرداندن) |
| ۱۱ | **چالش جاوااسکریپت یوتیوب برای نصب‌های pip** | باینری نصب‌شده با pip ماژول حل چالش (EJS) را همراه ندارد؛ استخراج/دانلود یوتیوب می‌توانست شکست بخورد | تشخیص خودکار نوع باینری (اسکریپت/zipapp در مقابل باینری مستقل) و افزودن `--remote-components ejs:github` با ترجیح `YTDLP_REMOTE_COMPONENTS` |
| ۱۲ | **پخش زنده و پریمیر** | دانلود بی‌پایان یا فایل ناقص | شناسایی `is_live`/`live_status` و رد با پیام فارسی |
| ۱۳ | **پیام‌های خام انگلیسی yt-dlp** | کاربر پیام «Sign in to confirm you're not a bot» می‌دید | ۱۶ قاعده‌ی ترجمه به فارسی همراه با راه‌حل (کوکی، پراکسی، نسخه، منطقه، فضا…) در `mapYtDlpError` |
| ۱۴ | **اعتماد به `info` ارسالی از کلاینت** | عنوان/کانال/کاور دلخواه در دیتابیس ذخیره می‌شد (کاور با `data:`/`javascript:`) | اعتبارسنجی و پاک‌سازی: محدودیت طول، حذف کاراکترهای کنترلی/جهت‌دهی، فقط http/https برای کاور |
| ۱۵ | **کاراکترهای جهت‌دهی متن در نام فایل** | می‌توانست پسوند واقعی فایل را در نمایش جعل کند؛ همچنین نام‌های رزرو ویندوز و طول نامحدود | `sanitizeFileName` بازنویسی شد (RTL/LTR override، CON/PRN/NUL، نقطه/فاصله‌ی اضافی، سقف طول) |
| ۱۶ | **پردازش ناقص هدر Range و نشت فایل** | `bytes=-500` و بازه‌های خارج از محدوده درست مدیریت نمی‌شد و با قطع اتصال کاربر، stream بسته نمی‌شد | `parseRangeHeader` کامل (۲۰۶/۴۱۶)، پشتیبانی `HEAD`، و destroy روی `req.signal` |
| ۱۷ | **نبود محدودیت نرخ** | هر درخواست یک فرایند سنگین yt-dlp/ffmpeg اجرا می‌کند | محدودکننده‌ی in-memory روی `info`/`jobs` با پیش‌فرض ۳۰ درخواست در دقیقه (`RATE_LIMIT_PER_MINUTE`) |
| ۱۸ | **استخراج تکراری اطلاعات ویدئو** | هر کلیک یک درخواست کامل به یوتیوب (کندی + ریسک محدودیت) | کش ۵ دقیقه‌ای با کلید شناسه‌ی ویدئو (`INFO_CACHE_TTL_MS`) |
| ۱۹ | **نبود بررسی مسیر فایل** | ارسال فایل بر اساس مسیر ذخیره‌شده در دیتابیس | بررسی `isPathInside` با پوشه‌ی همان job پیش از ارسال |
| ۲۰ | **`cleanYtDlpError` تهاجمی** | پیشوندهای `متن:` را از خطوط غیرخطا هم حذف می‌کرد | فقط خطوط `ERROR:` پاک‌سازی می‌شوند؛ در غیر این صورت آخرین خط دست‌نخورده برگردانده می‌شود |
| ۲۱ | **باگ‌های کوچک** | کد مرده‌ی پیشرفت، فرمت‌های «storyboard» به‌عنوان کیفیت، اعتبارسنجی ضعیف آدرس (پروتکل/طول)، تکرار لیست بیت‌ریت MP3 در دو فایل، ارقام لاتین در زمان نسبی، ناهم‌خوانی `themeColor` با پس‌زمینه | همه اصلاح شد؛ لیست بیت‌ریت‌ها تک‌منبع شد (`AUDIO_BITRATES`) |

## ۲) امنیت و پیکربندی

- **هدرهای امنیتی**: `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` و `no-store` برای API. عمداً بدون `X-Frame-Options` تا امکان نمایش در iframe/پیش‌نمایش از بین نرود.
- **`poweredByHeader: false`** و متادیتای کامل (OpenGraph/Twitter/robots/sitemap/icon).
- **Dockerfile**: کاربر غیر‌روت (`appuser`)، `HEALTHCHECK` روی `/api/health`، نصب yt-dlp با `--retry` و بررسی نسخه، و `drizzle-kit push --force` (بدون پرامپت تعاملی که می‌توانست کانتینر را معلق کند).
- **docker-compose**: healthcheck برای اپ، متغیرهای جدید، و مستندسازی حالت نمایشی.
- **`.env.example` و README** بازنویسی شدند (جدول کامل متغیرها، معماری، جریان کار، حالت نمایشی، آزمون‌ها). تناقض «دیتابیس الزامی/اختیاری» در README رفع شد.
- **CI**: مرحله‌ی «Unit tests» به گردش‌کار lint → typecheck → build اضافه شد.

## ۳) بهبودهای رابط کاربری و گرافیک

- **پوسته‌ی مشترک صفحات** (`page-shell.tsx`) و حذف کد تکراری بین `/` و `/preview`.
- **سربرگ بازطراحی‌شده**: بج معرفی، آیکون‌های یکدست (به‌جای ایموجی‌های نامتجانس)، سایه/گلو نرم‌تر.
- **دسترس‌پذیری**: `role="tablist"/"tab"/"tabpanel"`، `aria-selected`، حلقه‌ی `focus-visible`، لینک «پرش به محتوای اصلی»، `aria-live` برای پیام‌ها و `role="progressbar"` با `aria-valuenow`.
- **نمایش اطلاعات بیشتر**: سرعت دانلود و زمان باقی‌مانده، شماره‌ی نوبت در صف، حجم واقعی فایل، بج «پیشنهادی»، درجه‌بندی کیفیت (SD/HD/Full HD/2K/4K).
- **سیستم پیام (Toast)** برای موفقیت/خطا/اطلاع به‌جای شکست بی‌صدای درخواست‌ها، همراه با دکمه‌ی «تلاش دوباره» برای خطای دریافت اطلاعات.
- **نوار وضعیت سامانه** (yt-dlp، ffmpeg، دیتابیس، صف) از `GET /api/health`.
- **تاریخچه‌ی حرفه‌ای‌تر**: فیلتر همه/ویدئو/MP3، چیپ وضعیت، حذف دومرحله‌ای، ارقام فارسی.
- **تصاویر**: بارگذاری تنبل، `decoding="async"`، `referrerPolicy="no-referrer"` و جایگزین گرافیکی در صورت خطای بارگذاری.
- **ریزکاری‌های بصری**: احترام به `prefers-reduced-motion`، رنگ انتخاب متن، اسکرول‌بار سفارشی، تب‌های شیشه‌ای، کارت‌های با hover ملایم.

## ۴) معماری (بازآرایی برای تست‌پذیری)

منطق خالص از موتور اجرا جدا شد تا بدون اجرای yt-dlp هم قابل آزمون باشد:

```
src/lib/ytdlp.ts        موتور دانلود (اجرا/لغو/اطلاعات ویدئو)
src/lib/ytdlp-args.ts   ساخت آرگومان‌ها + ترجمه‌ی خطاها        (خالص/تست‌پذیر)
src/lib/progress.ts     پارسر پیشرفت yt-dlp                    (خالص/تست‌پذیر)
src/lib/files.ts        نام فایل امن، انتخاب خروجی، Range       (خالص/تست‌پذیر)
src/lib/toolchain.ts    کشف/نصب yt-dlp، ffmpeg و قابلیت‌ها
src/lib/jobs.ts         چرخه‌ی job، صف، حافظه‌ی زنده و دیتابیس
src/lib/demo-source.ts  کلیپ نمونه‌ی حالت نمایشی
src/lib/http.ts         ارسال فایل با Range/HEAD
src/lib/rate-limit.ts   محدودکننده‌ی نرخ
```

## ۵) آزمون‌ها

- **واحد (`npm test`)**: ۳۳ آزمون — پارسر پیشرفت (شامل سناریوی واقعی `137+140`)، نام فایل و Range، ساخت آرگومان‌ها و ترجمه‌ی خطاها، قالب‌بندی اعداد/زمان. اجرا با `node --test` بدون هیچ وابستگی تستی.
- **دود سرتاسری (`npm run smoke`)**: ۲۳ بررسی — سلامت سامانه، دریافت اطلاعات، ساخت job، پیشرفت میانی (سرعت/ETA)، MP4 و MP3 سالم، `HEAD`/`Range`، جلوگیری از دانلود تکراری، لغو و حذف.
- **حالت نمایشی (`DEMO_MODE=1`)**: امکان اجرای همین آزمون‌ها روی محیط‌هایی که به یوتیوب دسترسی ندارند؛ دانلود از یک کلیپ نمونه‌ی محلی (ساخته‌شده با ffmpeg) انجام می‌شود و کل مسیر yt-dlp/ffmpeg/صف واقعی است.

## ۶) پیشنهادهای باقی‌مانده (خارج از دامنه‌ی این تغییرات)

1. برای استقرار عمومی، احراز هویت (Basic Auth یا Reverse Proxy) اضافه کنید.
2. در صورت استفاده‌ی چند‌نمونه‌ای (multi-instance)، صف و حافظه‌ی زنده‌ی فعلی درون‌فرایندی است؛ برای مقیاس افقی به Redis/صف مشترک مهاجرت کنید.
3. ذخیره‌سازی فایل‌ها روی دیسک محلی است؛ برای حجم بالا از object storage استفاده کنید.
